# Colosseum 1.1.9: first-party updates

Status: isolated 1.1.9 client implementation. The new production Cloudflare route is
deployed but deliberately returns HTTP 503 until a real signed stable feed exists.
No 1.1.9 installer or released update is claimed.

## Distribution design

The 1.1.8 app uses the GitHub Releases latest API URL embedded in its executable.
1.1.9 instead checks:

    https://getcolosseum.world/updates/stable.json

This public URL is fixed for future versions. Cloudflare Pages now proxies it to
the public GitLab release-assets/stable branch, which serves:

    https://gitlab.com/kingoftheseas56/colosseum-site/-/raw/release-assets/stable/updates/stable.json?ref_type=heads

The JSON envelope uses the existing GitHub-compatible fields tag_name, draft,
prerelease, and assets. The updater preserves its existing signature checks,
SHA-256 validation, resumable downloads, and Windows installer bridge.
Only discovery and the verified notes URL allowlist have changed.

The future version-specific binary, signature and manifest will live on GitLab
release-assets/v1.1.9:

    releases/Colosseum-1.1.9-setup.exe
    releases/colosseum-update-v1.json
    releases/colosseum-update-v1.json.sig

The signed manifest binds the filename, size and SHA-256 of the installer.
Never treat unsigned stable.json as authorization to execute an installer.
Only a manifest verified with the embedded production Ed25519 public key
may select an automatic update.

Release notes for new versions must exist at a versioned first-party URL:

    https://getcolosseum.world/releases/v1.1.9

The legacy GitHub notes URL remains accepted for signed historical records.

## Install the Cloudflare endpoint without damaging the website

Source for the route:
scripts/update/cloudflare_update_route.mjs

Add the exported function to the existing Pages advanced Worker bundle or
inline it. Before the current website handling, call:

    const updateResponse = await serveStableFeed(request);
    if (updateResponse) return updateResponse;

Then continue the existing HTML and env.ASSETS.fetch(request) handling.
Do NOT replace or redeploy the website assets blindly. Preview first.

Production route preparation was deployed as Pages deployment
298eb468-ef9f-402d-8c2e-762b506cd495, from preview
157fe97d-3ed6-4236-a7aa-6f7e25bd2c32, with the unchanged website
SHA-256 d1252ea09d3c78b61ec5aee969f2a2acd20e9a2441494babb98c9956f293a1c5.
Because no signed stable release has been promoted, live GET to this route
currently returns 503 (Cache-Control: no-store). This is intentional.

The route forwards small JSON responses with ETags, rejects unexpected HTTP
methods, follows no unexpected redirects, and fails closed with HTTP 503 if
GitLab's stable feed does not exist or is malformed. No fabricated 1.1.9
release should be served before the actual binary and signing are ready.

Run route fixture checks:

    node --test scripts/update/test_cloudflare_update_route.mjs

## Signed stable publication, in safe order

1. Build and runtime-test a real 1.1.9 Windows installer. Preserve its
   exact installer size, SHA-256, and source/build provenance. Do not reuse the
   inert installer hash from resources/installed-chronicle.
2. Author release/presentation/1.1.9.json with first-party notes URL.
   Use the existing production Ed25519 private key from secure local storage;
   NEVER commit or reveal it. Ensure the derived public key matches
   native/update/UpdatePublicKey.h. Do not rotate signing trust.
3. Run scripts/update/generate_update_manifest.py to generate signed
   colosseum-update-v1.json and its raw 64-byte .sig.
4. Run scripts/update/verify_update_release.py using the matching public DER,
   installer, manifest, signature and optional artwork.
5. Upload all exact verified files to GitLab release-assets/v1.1.9 under
   releases/. Use Git LFS for the installer if necessary. The signed JSON
   and signature must retain their exact raw bytes.
6. Download those files back without authentication and verify size/SHA-256,
   signature, and that HTTP Range/If-Range downloads are handled safely.
7. With the verified local files, generate the stable envelope (this tool does
   no upload and will not overwrite a pre-existing output):

    python scripts/update/create_stable_feed.py ^
      --manifest STAGE/colosseum-update-v1.json ^
      --signature STAGE/colosseum-update-v1.json.sig ^
      --installer STAGE/Colosseum-1.1.9-setup.exe ^
      --public-key-der SECURE/public.der ^
      --asset-base-url "https://gitlab.com/kingoftheseas56/colosseum-site/-/raw/release-assets/v1.1.9/releases?ref_type=heads" ^
      --output STAGE/updates/stable.json

8. Verify the first-party version-specific release-notes page and deploy the
   Cloudflare update proxy to a tested preview, then production.
9. LAST, publish the verified updates/stable.json file to the public GitLab
   release-assets/stable branch. This single file flips the offered version.
10. Test the public first-party endpoint GET/ETag response, downloaded bytes,
    and signed release integrity, then perform an actual clean installed
    Windows 1.1.9 update-and-restart trial. Publish the release announcement
    only after these checks pass. No GitLab CI is required.

The order matters: publishing stable.json before the binary/signature is
downloadable would advertise an update that cannot succeed.

## Migration boundary

Existing 1.1.8 binaries still use the GitHub Releases API. Its current public
response is 404, so we cannot retarget installed copies remotely. A one-time
manual Windows install of 1.1.9 is required unless GitHub restores the original
API path. Subsequent Windows updates can then use our first-party feed.

Linux 1.1.9 must remain manual-only. Signed schema v1 describes one Windows
EXE and the Linux updater correctly refuses to select or run that installer.
A platform-aware schema and separate install bridge are required before
promising automatic Linux updates.

Rollback is restoring the previous verified stable pointer or reverting the
Cloudflare Pages Worker. Do not serve a fake release or downgrade users.

## Outstanding gates

- Production private-key custody and valid matching 1.1.9 signature
- Real release notes page and official 1.1.9 Windows installer
- Cloudflare Pages production Worker integration and first-party live route
- Public remote installer byte-for-byte and signature verification
- Full installed-Windows updater trial, including failure recovery

Until these gates pass, the updater code is implemented but 1.1.9
auto-update distribution is not qualified or published.
