# Independent review: Workers + Neon Free PostgreSQL + R2 Standard
**Official terms checked 2026-10-14. Verdict: CONDITIONAL staging candidate; REJECT as a guaranteed hard-$0 production foundation and REJECT at 5,000 DAU × 30 Worker requests/day.** Only the specified combination was assessed. No account, code, data or deployment was changed. All performance projections below are arithmetic or design proposals, never run benchmarks.

## 1. Official free limits, traps and unverified eligibility
- **Workers Free [W]:** 100,000 requests/day **across the account**, resetting midnight UTC; exceeding gives error 1027. CPU time **10 ms per request**, 128 MB isolate memory, 50 external subrequests/invocation and six simultaneous outgoing connections awaiting headers. CPU excludes network waiting, not JSON processing or complex validation. Other existing Workers share the 100k budget. Fail closed on protected routes; fail-open bypass is unsuitable.
- **Neon Free [N]:** $0 recurring, no card and no trial deadline; **1 GB database storage/project**, capped at **20 GB account-wide**, **100 CU-hours/project/month**, **5 GB outgoing public data/project/month**, up to 2 CU, 10 branches/project, automatic compute suspension after 5 minutes idle, 6-hour restore window (up to 1 GB changes), one manual snapshot, community support, no free-plan uptime SLA. Neon increased storage from the formerly cited 0.5 GB to 1 GB in October 2026. If CU-hours or egress run out, **Neon suspends compute** until next period/upgrade. Storage-increasing operations fail at 1 GB/project or 20 GB total; data is not deleted. Egress means database-to-Worker/public, NOT necessarily the full client response bytes.
- **Important Neon compute model:** 100 CU-h buys **400 active hours/month at 0.25 CU**, approximately 13.3 h/day. An always-awake database at 0.25 CU would use ~182.5 CU-h over 30 days, exceeding Free even with modest request volume. Auto-scaling above 0.25 CU worsens this. A request stream with fewer than five idle minutes can keep it awake. This is arithmetic, not an observed usage profile.
- **R2 Standard [R]:** **10 GB-month** storage, **1m Class A** operations/month (including object PUT/LIST), **10m Class B**/month (GET/HEAD), **no R2 egress fee**. Beyond allowance metered at $0.015/GB-month storage, $4.50/million A and $0.36/million B, with billing-unit rounding. The free allowance excludes Infrequent Access. Two retained content versions count toward storage. These are free *allowances*, not a published automatic spending shutdown.
- **Billing/activation [G,B]:** R2 must be activated through a **subscription checkout**; Cloudflare billing says a primary payment method is required to purchase services. Whether this particular account can activate R2 without a payment step is unverified (subscription read denied). No spending, signup or activation authorized. Account R2 is still disabled. Do not mistake an included free tier for a zero-liability account.
- **Workers Cache [C]:** its front-of-Worker cache can skip Worker execution/CPU on GET/HEAD cache hits, but **every hit still counts as a Worker request**. Cache has no magic bypass for 100k/day; HTTP Cache API used *inside* a Worker invokes code first and is per-data-center. Cached lease-protected content must never bypass authorization accidentally.

**Strict-$0 conclusion:** Workers/Neon Free enforce limits by errors or suspension; R2 can incur metered overages. A universal hard-$0 guarantee is unsupported. Publishing caps, operation budgets, private-only object access, quota monitoring and deliberate fail-closed behavior reduce risk but sacrifice availability; billing alerts alone do not make hard caps. No trial credits are used in this assessment.

## 2. Initial 165–250 MB / 1.13m-row import: plausible without 53 days, unproven
**Supplied audited baseline, not independently re-inspected:** four SQLite DBs 164,626,432 bytes; 24 tables and 1,133,337 rows. D1 source-index plan implies 2,823,109 writes before controls, ~3.18m with 32-row chunk ledger; ~53 days at 60k/day. Current Workers+D1 staging has 24,208 rows in 10 complete tables, 14 tables outstanding; 7 Worker and 10 publisher tests pass. Neither Neon nor R2 is configured or benchmarked.
- **Why Neon differs:** PostgreSQL does NOT inherit D1's 100k row-write/day quota. An authorized publisher can bulk-load normalized data using PostgreSQL COPY or bounded multirow inserts through a proper database connection, build indexes and ANALYZE afterwards. This is ordinary operation of a different datastore, not a D1-quota workaround. Do not issue millions of Worker HTTP calls or one R2 PUT per individual relational row.
- **Time thresholds, not measured performance:** to ingest 1,133,337 rows in one hour requires ~315 rows/sec; six hours ~53 rows/sec, excluding index builds and recovery. No actual loading speed, Neon CU-h, transfer bill, or elapsed time is established. Test representative bulk load and index build before promising a same-day cutover.
- **Postgres storage unknown:** 165 MB SQLite is NOT equal to Postgres heap + TOAST/JSONB + multiple indexes + staging branch. Full-table recreation or double-loading may exceed Neon Free's 1 GB/project. A thin indexed search/lookup/facet projection is more defensible, with rich per-title/per-issue JSON in R2, but only if every consumer query is equivalent. Require measured pg_database_size, per-relation/index sizes, publish-version peak, projected growth and retained-rollback headroom.
- **R2 object tradeoff:** 1,133,337 separate object PUTs would already exceed the **1m/month Class A** free allowance before retries/updates. *Illustration:* 100 rich records per immutable object would need ~11,334 PUTs, but retrieving one record fetches a larger shard and hurts selective read amplification. Group by title or bounded issue/edition page based on measured cardinality; users must receive only single records/pages through the Worker, NEVER an underlying shard, DB or content pack. R2 shards are for server storage only, not a server-side full-scan search index.
- **Acceptance gate, not executed:** deterministic per-table fixtures, bulk-load sample then full projection, count/hash reconciliation, sampled SQL EXPLAIN ANALYZE, Neon billed bytes/CU-hour, index build cost, failed-batch resume and storage high-watermark. If index sizes or parity fail, this design fails. No free-tier import exemption was assumed.

## 3. Exact native query dependencies and parity test
PostgreSQL can implement indexed search, rank sorting, AND facets, relational joins, stable cursor pagination and exact IDs. It does **not** automatically replicate SQLite collation/FTS/order/NULL rules or synchronous native calls.
| Observed supplied table families | Proposed essential indexed relationships | Risk if projected too far |
|---|---|---|
| IMDb title 61,585; genre 143,615 | title IDs, names, rank/year/type fields, genre-to-title + reverse joins | combined genres, sort/tiebreaker and precise ID lookups |
| MAL anime 20k, manga 20k; tag 127,417; classification 127,417 | two catalogue IDs/types, tags/classifications via indexed postings, bounded AND facet semijoins/HAVING | accidental OR semantics, lost facets/score ordering |
| Comics series 22,710; canonical issue 55,598; downloads 57,432; mirrors 398,427; curated series 1,134; curated editions 9,655 | series/issue/edition joins, curated coverage, source-specific mirror/download resolution and stable ordering | dropping mirror/edition relationships breaks fallback and issue selection |
| Tankoban series 10k; volumes 28,839 | indexed series IDs, volumes and ordering/numbering fields | inaccurate volume synthesis and ordering |
| Remaining of 24 tables, Biblio, universe endpoint families | inventory every actual SQL call and field before any omission | numbers supplied do NOT prove complete coverage |

Build a source-table→query→native method→endpoint dependency matrix for all existing C++ search, ranked lists, ID lookups, AND facets, genre joins, downloads, mirrors, curated and volume-synthesis paths. Golden tests must compare actual returned IDs, ordering, counts, NULL handling, facets and pagination against SQLite. Use parameterized fixed SQL query templates, sort/field allowlists, index plans and hard page caps; run worst-case joined facet benchmarks only on representative indexed data. No client-side table scans or downloading an SQLite database.

**Remote performance reality:** Workers execute at global edges; Neon compute resides in a region and scales to zero when idle. Uncached requests may cross regions, incur cold starts and make multiple SQL/R2 calls. Database placement, cache ratios, tail latency and client geography are unknown. No live p50/p95, geo or cold-cache tests were run. Measure at likely user regions, first request after ≥5-minute idle, and cached/warm and cold/uncached cases before choosing.

## 4. Selective read API, content publishing, security and offline design (proposal)
1. **Native:** migrate the relevant existing Qt/C++ synchronous SQLite calls to nonblocking remote adapters with cancellation, timeouts, bounded retries/backoff, cursor page limits, validators, ETag/TTL and last-good offline *record/page* caches. Preserve local-first user identity, library, history, progress, preferences; Vault remains authoritative locally. Deliver Tankoban, Biblio, Theatre and Universes selectively; Tributes are independent styled franchise experiences. Native renderer changes require app releases. **1.1.9 excludes Feria and Vinyl**.
2. **Read Worker:** fixed route/schema/query allowlists; SQL parameter binding, indexed ranked/faceted searches and IDs; retrieve only requested rich R2 objects, return bounded JSON not raw object shards or full content packs. Secrets and Neon credential are server-side; read-only database role. Keep publisher/admin credential completely separate. R2 binding/private bucket unless deliberately public assets approved. MusicBrainz public API is an explicitly bounded, cached enrichment (Wikidata optional), not a full metadata mirror.
3. **Publishing:** immutable, separate Universe and Tribute manifests with schema version, minimum native renderer capability, content hashes, external asset URLs, object inventory, source provenance, record count and catalogue version. Stage new Postgres projection and versioned R2 JSON first, verify links/objects and counts, then make an **atomic Neon current-version pointer** change. R2 and SQL are NOT one transaction: retain prior files + SQL version, use checksum and read-after-publish validation, rollback pointer if corrupt, old content retained through cache TTL. Version-keyed ETags prevent clients mixing content generations.
4. **Guest read tokens:** no third-party registration. Worker issues short-lived, rate-limited anonymous HMAC read leases (e.g., 30 minutes), protected routes verify before serving. No privileged static key, Neon URL or publisher secret in inspectable C++ binary. **Production guest issuer is currently missing**, despite reported staging tests. Per-route limits, page bounds, anti-replay heuristics and abuse telemetry cannot guarantee app-only access.
5. **Desktop identity limit:** the desktop application can be copied, modified or emulated; User-Agent, CORS, embedded credentials, signatures and issued bearer tokens are **not proof** that a request came from an authorized Colosseum instance. Treat guest content as publicly retrievable and resistant to scraping only by throttling. Truly restricted content cannot rely on anonymous 'app-only' as a security boundary. Never put private local history or user identity into shared edge cache. Front-of-Worker caching of authorization-protected responses risks bypassing token checks; cache publicly shareable published pages only with explicitly safe access/version semantics, or authenticate first inside Worker.

**R2 pending:** do not activate or assume it exists. Preserve deployed D1 staging untouched. A separately approved Neon prototype may temporarily store a small bounded rich JSON subset in Neon and reference lawful external asset URLs, while staying below 1 GB; do not publish manifests with nonexistent R2 references. Once R2 is actually activated with verified billing consent, populate objects, verify hashes and old/new parity, then change a versioned Worker backend read pointer after a rollback path is proven. No account provisioning, writes to source data, migration or deployment were done here.

## 5. DAU sensitivity (arithmetic; 30-day month)
Assume 30 dynamic API requests/user/day and 20 KB compressed **client response**. API transfers to clients are NOT automatically Neon egress; R2 asset traffic is separate.
| DAU | Worker API requests/day | API requests/month | compressed response/month | Workers 100k/day |
|---:|---:|---:|---:|---|
| 100 | 3,000 | 90,000 | 1.8 GB | fits absent other traffic |
| 1,000 | 30,000 | 900,000 | 18 GB | fits, shares account allowance |
| 5,000 | **150,000** | 4,500,000 | 90 GB | **FAILS by 50k/day even if cache hit 100%** |

Let h = cache-hit fraction, q = Neon SQL statements per backend miss, b = R2 GET/HEAD ops per miss. **Monthly backend misses = requests × (1-h); Neon SQL count = misses × q; R2 Class B = misses × b**. For h at **0% / 50% / 90%**: 100 DAU incurs **90k / 45k / 9k** misses; 1,000 DAU **900k / 450k / 90k**; 5,000 DAU **4.5m / 2.25m / 450k** (last case fails Worker cap first). At 1k DAU, h=50%, q=2, b=2 ⇒ **900k SQL queries + 900k R2 B** per month. At 5k DAU h=0%, b=3 ⇒ **13.5m R2 B**, above free allowance.

**Neon outgoing bytes are a separate limiter:** 5 GB divided by 900k misses at 1,000 DAU, 0% hit gives only ~5.6 KB PostgreSQL data per miss before other project egress. At 5 KB Neon result/miss that case uses **4.5 GB/month**; 5,000 DAU at 50% hits uses **11.25 GB** and suspends Neon Free. At 20 KB returned from Neon per miss, 1,000 DAU and 0% hits would need **18 GB**, already infeasible. Returning lean index keys and moving rich content to R2 plus measured cache efficacy matters. CU-hour exhaustion can still occur before these byte limits.

**Assets separately, hypothetical:** 5 asset GETs/user/day = 150k requests/month at 1k DAU or 750k at 5k DAU, before bots/hotlinks. A 2 MB average object would imply 300 GB/month delivered at 1k DAU, with free **R2 egress**, but GETs consume Class B on cache misses. If GETs use Workers they consume the same **100k/day** Worker budget; direct public R2 delivery avoids Worker invocations but weakens lease enforcement and can incur metered R2 operations. R2 object size, asset demand, cache-hit rate and hotlink abuse are all unknown, not free-performance guarantees.

## 6. Failure modes, portability, tradeoffs and final verdict
**Failure modes:** Workers 1027 and 1102; account-wide quota exhaustion/bots; Neon egress or compute suspension; one-GB Postgres cap; regional roundtrip and 5-minute cold starts; slow AND-facet/genre join; R2 unregistered or subscription blocked; unbounded Class A/B/storage bill; stale cached manifests, broken objects, mismatched SQL↔R2 versions, partial importer resume, guest token replay, offline client. Fail closed, use local last-good bounded pages, limit query cost and quotas, immutable publish IDs/checksum gates, and keep tested rollback pointer. None creates free-tier SLAs.

**Migration/portability:** material effort (SQLite SQL/FTS semantics, 24-table dependency audit, Postgres schemas/indexes, publisher conversion, Qt/C++ asynchronous state machine, client offline cache, guest token issuer, object-publish transaction protocol, controlled backend switch). PostgreSQL export is portable and R2 offers S3-compatible object patterns; Workers bindings/cache/auth, URLs and deployment are Cloudflare-specific. No live integration or production-readiness verified.

**Three decisive tradeoffs:** (1) PostgreSQL bulk import **can eliminate the D1 per-row quota calendar delay**, but must prove 1 GB storage/100 CU-hour fit; (2) expressive joins and facets avoid feature-loss pressure yet add remote latency, Neon 5 GB egress and cold compute; (3) R2 gives inexpensive selective JSON/assets and free egress, but its **metered subscription and no hard-$0 guarantee** conflict with strict risk-free infrastructure.

**An alternative that could beat it:** Workers + D1 + Workers Static Assets (NO R2) avoids the R2 subscription/metering risk if the feature-equivalent searchable projection is demonstrably small enough and static assets can serve versioned content; it still must solve the ~2.82m D1 indexed writes without client bulk downloads or lost search/mirror parity. Workers + D1 + R2 eliminates the extra Neon quotas/provider/latency and reuses present D1 staging, but inherits the unproven 53-day import path and R2 exposure. Neither fixes **5k × 30** Worker hits/day.

**Final disposition: CONDITIONAL only for measured, controlled staging and perhaps 100–1,000 DAU with safe headroom. REJECT unconditional guaranteed-$0 production and 5,000 DAU under fixed workload.** Release decision remains gated on Neon storage/compute/egress/import measurement, native feature-parity results, approved R2 billing/limits, public guest token issuer, offline and rollback tests. No tests, data migration, source edits, new services or deployment performed.
