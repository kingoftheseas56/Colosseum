# Independent review: Cloudflare Workers + D1 + Workers Static Assets, NO R2
Checked 2026-10-14. Official provider-documentation desk review; NOT a deployment, import, benchmark, test run, live account/billing verification or production-readiness claim. Supplied dataset and staging facts are not independently remeasured.

## Executive verdict
**REJECT as the sole durable full-scale backend for the specified workload; CONDITIONAL bridge while R2 is pending.** Free Static Assets can distribute versioned public Universe/Tribute JSON and precomputed catalogue pages, and D1 can support smaller selective indexed queries. But the original indexed import needs weeks under D1 Free writes, the 20,000-assets-per-version cap blocks one file per title, and 5,000 DAU × 30 dynamic API requests/day exceeds the 100,000/day Worker limit. No full feature-parity, cross-region performance or native C++ integration has been proven.

**Three decisive tradeoffs:** (1) indexed D1 import quota; (2) Static Assets file count versus selective per-record retrieval; (3) Worker invocations and D1 scan budgets despite caching. The trade is worth accepting only as a short-lived, bounded R2-free stage, not a complete catalogue migration.

## Bootstrap: full 24-table copy is architecturally disqualified
Task-supplied verified baseline: four SQLite databases total 164,626,432 bytes (~157 MiB), 24 tables, 1,133,337 rows. Source indexes imply ~2,823,109 D1 writes before control overhead, ~3.18m including the 32-row-chunk ledger. At the full 100k/day allowance, minima are ~28.3 and 31.8 days; at the conservative 60k/day publishing budget they become ~47.1 and ~53.0 days. These are counted-row quota calculations, NOT measured execution time. Even 1.13m one-write rows require 11+ fully-utilized days. Index creation, SQL dump import, multiple workers or INSERT batching have no documented charge exemption.

Minimum logical-title projection alone spans IMDb 61,585 + MAL anime/manga 40,000 + comics series 22,710 + Tankoban series 10,000 = **134,295 distinct world-title records**, not counting mirrors, facets, issues or volumes. At one logical row plus ONE indexed-column entry each, an illustrative ~268,590 writes needs at least three 100k days or ~4.5 days at 60k/day. With three indexed entries/title, ~537,180 writes needs ~9 conservative days. Actual index/FTS5 writes can be higher or differ; obtain meta.rows_written rather than treating this illustration as proof. A three-day 60k/day objective needs <=180k measured D1 writes across schema, data, indexes and control updates.

**Proposal:** retain in D1 only a feature-complete compact searchable/rankable projection and ID/facet locators. Store rich public per-series/issue JSON as versioned assets. Static asset uploads do NOT consume D1 rows written; the D1 projections, aliases, rank keys, facets, publish pointer and any indexing do. This reduces the import problem only if every remotely filterable field has a genuine server-side search representation. Do not move filtering to client full scans, omit mirror/genre tables, ship full DBs/content packs after release, or call an incomplete projection feature parity.

Existing deployed baseline is two protected staging D1 databases, 24,208 rows in 10 small complete tables, 14 unimported tables, cached MusicBrainz enrichment, seven passing Worker tests and ten publisher tests. The production guest issuer and native adapter are missing. No tests or imports were performed for this review.

## Feature-contract matrix: exact dependencies to prove
| Native feature | Necessary remote data/query shape | Required comparison to current local SQLite |
|---|---|---|
| ID lookup/canonical detail | Indexed (world, source, ID), aliases, rich record locator and typed nulls | Match IDs, canonical joins, not-found and field semantics |
| Indexed search, ranking, deep pages | D1 term/prefix/FTS5 search, stable rank and deterministic tie-break, cursor/keyset pagination; fixed popular list pages may be static | Same results/order/page boundaries; EXPLAIN QUERY PLAN and actual row-read metrics |
| Genres and AND facets | IMDb genre 143,615; MAL tag 127,417 plus classification 127,417 represented in server-side join/postings/indexes | Exact AND intersection, genre joins, counts, multi-facet combinations |
| Comics sources and issues | Comics download 57,432; download_mirror 398,427; canonical_issue 55,598; per-parent rich JSON plus remotely searchable fields where required | Source/mirror selection, issue filters, correct page and order; no bulk mirror table transfer |
| Curated coverage | Comics curated_series 1,134 and curated_edition 9,655 mapping + issue/series links | Curated member sets and coverage/order match |
| Tankoban volumes | Series 10,000 and volumes 28,839, bounded per-series arrays plus lookup keys | Volume synthesis, missing ranges, IDs and sort match |
| All worlds and special experiences | Tankoban, Biblio, Theatre, Universes, Vault differentiated; Tributes separate from Universes | Scene-schema versions and compatibility; Vault/local user state never replaced by server |

These are *proposed* table dependencies. A real C++ SQL-call inventory and differential tests against original query outputs are mandatory before reducing 14 unimported tables. FTS5 is supported by D1's SQLite-derived engine, but rank semantics, compound predicates, index-write amplification and p95 cost still need testing. Avoid '%term%' full scans, OFFSET-heavy deep paging, unindexed joins and sorting huge result sets in Worker. Indexed search can still read many rows if filters/order are wrong.

## Static asset design: selectively served, versioned, no packs
Direct '/content/vN/world/list/page-XX.json', Universe/Tribute manifest/scene JSON, artwork and cached non-sensitive public data fit asset-first delivery. The native renderer consumes validated declarative content only; a new QML render capability still needs an app release. Dynamic '/api/v1/search', combined facets, source lookups and guest leases invoke Workers; carefully set worker-first rules for '/api/*' to prevent static path collisions that bypass auth. Do not let SPA 200/HTML fallback masquerade as a missing JSON document.

**Per-file barrier:** 134,295 title records cannot be represented as 134,295 individual Static Asset files: Free permits 20,000 per Worker version *for everything*. At least ceil(134295/20000)=7 logical titles per physical file on average, even before pages/manifest/images. Large publicly downloadable shards would overfetch unrelated content and approach the forbidden pack model. Acceptable candidates: bounded list pages served directly as assets, and internally fetched small sharded JSON via env.ASSETS.fetch() where Worker extracts just one requested rich record and sends only that JSON. This latter path is still metered as a Worker call and needs measured CPU, memory, HTTP handling, and cold-shard costs; there is no built-in Static Assets query engine. Putting every detail in D1 instead reintroduces row-write/storage pressure. A 25 MiB asset is an upper size limit, not a sensible record-page size.

**Publisher/version protocol (not implemented):** generate deterministically sorted documents and manifest, validate schema, referential links, size and stable IDs; hash each asset and build signed/hashed version manifest. Deploy an asset collection with both new and rollback-version files, smoke-check assets, then atomically update a tiny D1 published-version pointer. Pin paged API sessions to one content generation, use content-hashed URLs with suitable ETag/immutable cache policy, retain old asset paths within the 20k budget, and reverse the pointer on failure. Revert the Worker version separately if necessary: Worker version rollback does **not** revert D1 storage or metadata. A new backend asset deployment is allowed without a desktop release; do not execute remote QML/scripts or treat a content schema change as a new native feature.

**Guest/security truth:** no third-party account and no privileged key baked into C++. Worker can grant short-lived anonymous guest leases (staging already has HMAC lease work) and impose request budgets; an attacker can still clone the protocol because a publicly distributed desktop app cannot prove app-only origin. CORS, User-Agent and public-key-in-app checks are not caller authentication. Static asset-first URLs are public and cannot have per-user Worker authorization while bypassing the Worker. Keep admin/publisher secrets and routes strictly server-side, use fail-closed behavior, avoid per-request D1 abuse-counter writes, and never publish a secret as a static asset. Validate schemas and hashes on client; protect publishing, not user identity via catalogue metadata.

**Offline and local authority:** replace synchronous local SQLite calls with asynchronous bounded Qt networking adapters: cancellation, timeouts, backoff, stable cursors, ETag/TTL and bounded offline cache, deterministic error/incomplete states, snapshot/version pinning and stale-last-good fallback. Local identity, library, history, progress and preferences stay authoritative. This service must not cause post-release DB download. MusicBrainz remains public-API cached enrichment with optional Wikidata, not a full mirror. External artwork URLs may fail and need placeholders; no upstream uptime or API entitlement has been established here.

## Sensitivity at 100 / 1,000 / 5,000 DAU
Assume 30 **dynamic** API calls/user/day with a 20 KB compressed response, and define h as Worker-side cache hits BEFORE querying D1, not before invoking Worker. Let A be **scanned** D1 rows across all SQL for an uncached dynamic call. Worker calls N=30×DAU; D1 scanned rows N×(1-h)×A. All traffic/response numbers below are calculated scenarios, not measurements. MB decimal; excludes asset traffic, issuance, admin and other Worker usage.

| DAU | Worker calls/day | Dynamic bytes/day | D1 rows at A=50, h=0 / h=80% | D1 rows at A=250, h=0 / h=80% |
|---:|---:|---:|---:|---:|
| 100 | 3,000 | 60 MB | 150k / 30k | 750k / 150k |
| 1,000 | 30,000 | 600 MB | 1.5m / 300k | 7.5m / 1.5m |
| 5,000 | **150,000: FAILS Worker Free** | 3,000 MB | 7.5m / 1.5m | 37.5m / 7.5m |

D1 Free's 5m/day budget allows ~166 scanned rows/request at 1k DAU with no cache hits, or ~833 rows per MISS at 80% Worker-cache hits. At 5k DAU with 95% hits and A=250, D1 would scan 1.875m rows, BUT the 150k Worker invocations still fail. At least 50k (>33.3%) of those 150k calls must be suppressed *before Worker entry* by actual local cache or replaced with genuinely direct static assets; leave additional headroom for other account traffic and guest issuers. The Worker Cache API avoids D1 lookups but does not save Worker-invocation quota. Static asset traffic is separate and directly served requests are free/unlimited per documented pricing, within file/count/public-access limits; it is not a substitute for arbitrary AND search.

## Latency, failure modes, migration and portability
Static assets use globally distributed caching; geographical first-request/cold-cache latency is not measured. D1 can involve a remote primary and its eventual replica settings/consistency cannot be assumed configured on this account. D1 indexed SQL overhead, multi-join AND search, FTS ranking, Worker JSON parsing against a 10 ms CPU budget, and external media hosts could all dominate p95 in India or elsewhere. Benchmark p50/p95 for cold and hot paths, at least geographically distinct test clients, plus Worker CPU, DB meta.rows_read/written and byte/read amplification. No current live-performance claim is made.

Principal failure modes: quota 429/1027 and D1 row errors; 500MB/db storage, write budget shared with publish/version churn, 20k file and 25MiB asset limits, partial new manifests, old-client 404 on asset retirement, stale caches, attacker replay/cloning, D1 hot/remote-primary contention, lack of connectivity and public URL leakage. Fail closed on admin/API auth, serve explicit API failures/offline cached data rather than silently empty lists; enforce tight publisher validation and don't put canonical DB files or private assets in asset directories.

Engineering effort is high: inventory current queries; build compact projections without omissions; measure exact index/FTS writes; build deterministic rich-record publisher and version manifest; stage/rollback atomicity; native Qt asynchronous adapters and caches; differential parity fixtures; cold/warm regional latency and load/abuse tests. Existing 17 staging tests do not establish any of these outcomes. Keep schema/record IDs, portable SQL migrations, JSON manifests and publisher output under version control or normal local backups; keep asset origins manifest-configurable so the desktop app is not hardcoded to one host.

**R2-pending transition:** current protected Worker/two D1 staging DBs may remain in place with only small complete tables; a parity-proved compact index plus bounded public static content can be phased in after the parent authorizes deployment. No R2 calls, provisioning or 1.1.9 scope expansion now. **Which alternative beats this:** Workers + D1 + R2 Standard after activation better supports individually-addressable rich JSON objects, independent content publication and no per-Worker-version 20k-file ceiling. That alternative needs separate eligibility/billing/overage checks (R2 activation is pending), and does NOT bypass either Workers invocation quotas or D1 read/write quotas. Do not label it guaranteed hard-$0.
