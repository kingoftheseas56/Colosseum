# Verdict
**REJECT as a durable, all-free full-catalogue production foundation; CONDITIONAL FIT for a small pilot** subject to measured fit and parity. Supabase removes D1's specific daily row-write bootstrap obstacle, but substitutes 500 MB Postgres, 5 GB uncached monthly egress, 500,000 monthly Edge Function invocations, limited Storage, and possible free-project pausing. Cloudflare Worker Free helps with cacheable public responses but cannot fix those limits or its own 100,000 inbound requests/day cap.
**Three decisive tradeoffs:** (1) fast *possible*, not verified, PostgreSQL COPY import versus tight final DB/index size; (2) normal SQL joins/ranking/facets versus low egress and shared compute; (3) unified API/DB/assets versus inactivity pauses, no automatic free DB backups, and migration away from already-staged D1.

# 1. Official quotas, restrictions, $0 risk
**Observed official [S1,S2,S4]:** Supabase Free permits 2 active projects; dedicated Postgres with shared CPU and 500 MB RAM, 500 MB database size/project, unlimited Data API requests (not unlimited compute or transfer), 50,000 monthly active Auth users, 1 GB Storage, max 50 MB individual Storage upload, Basic CDN (not paid Smart CDN), 5 GB uncached egress plus 5 GB *Storage CDN cached* egress/month, 500,000 Edge Function invocations/month, 1 GB logs ingestion, no automatic DB backups and no paid uptime SLA. Edge functions are capped at 256 MB memory, 150 seconds free isolate wall-clock, 2 seconds active CPU per request and 150 seconds request idle timeout. Function/REST response bytes ordinarily use **uncached** egress; Storage cached allowance is NOT extra API egress.
**Observed official [S1,S2]:** On Free, database size above 500 MB puts Postgres in read-only mode, independently of the included 1 GB disk space; organization-level fair-use restrictions for DB size can cause HTTP 402. Free projects can pause after roughly seven days of insufficient DB activity. Traffic bursts, CPU, quotas and provider fair-use limits are availability risks; no guaranteed always-on or free throughput promise.
**Hard $0:** Official Supabase policy says Free is not charged for over-usage; instead usage can be restricted/degraded. Paid subscriptions, billable add-ons, trial/temporary credit foundations and storage or compute upgrades are **excluded**. Pro Spend Cap is NOT a Free feature. Account/card state was inaccessible and no subscription/payment checks or account changes were performed. Staying Free can keep spending at $0, but cannot guarantee service at any arbitrary traffic level. No price is assumed for outages or fallbacks.

# 2. Bootstrap, projection, write-accounting
**Supplied verified facts:** Four SQLite DBs = 164,626,432 bytes (164.63 MB decimal, 157.0 MiB), 24 tables, 1,133,337 rows. D1 indexed writes estimated 2,823,109 before controls, about 3.18 million with 32-row chunk ledger, translating to ~53 days at conservative 60,000/day. Current *separate* D1 staging has 24,208 rows in 10 small complete tables with 14 not imported; 7 Worker and 10 publisher tests passed. None proves Supabase readiness.
**Official [S3]:** Supabase supports native PostgreSQL COPY and pgloader bulk import rather than a one-API-insert-per-row migration; no D1-style per-index-row daily SQL-write quota is published for Supabase Free. **Therefore the ~53-day D1 import calculation does not transfer.** This is not an exemption or a speed guarantee. Shared compute/RAM, SQL timeouts, indexes, WAL, disk and 500 MB read-only risk can still interrupt the import. No import elapsed time can be claimed without running one.
**Proposed evidence gate:** Produce 24-table column/key dependency ledger. Convert SQLite to typed/stable-ID PostgreSQL extracts; bulk COPY in restartable controlled batches, validate count, FK/ID coverage, search/rank/facet results and SQL ordering; build only required indexes, ANALYZE, compare queries with actual C++ SQLite contracts. Measure pg_database_size, pg_total_relation_size, index bytes after full load and after indexes, plus peak staging/WAL/operations and actual completion time on Free.
**Size sensitivity:** 500 MB Postgres ceiling is only ~3.04x the present SQLite file total, or 2x an expanded 250 MB source. SQLite includes its own index bytes, so Postgres ratio is unknown. Purely illustrative ratios of 2x/3x/4x give ~329/~494/~659 MB, not forecasts. Require **measured <=375 MB after full indexes** (proposed 25% headroom) or reject rather than relying on near-500 MB read-only behavior. Simultaneously holding two full DB revisions for rollback may itself exceed quota.
**Projection catch:** Known title-like entries = IMDb 61,585 + MAL anime/manga 40,000 + comics series 22,710 + Tankoban 10,000 = 134,295, NOT the full source/unique-ID tally. Hypothetically storing 8 KB of rich JSON for each = ~1.074 GB, already above Supabase Storage's 1 GB quota before Universe versions/art; content sizes are unmeasured. Keep only necessary search projections in Postgres and selective rich records in Storage. Removing relational downloads/mirrors/tags may destroy query parity or add multiple object requests; no arbitrary cut is acceptable. No bulk DB/content-pack delivery to clients.

# 4. API, public desktop identity, versioned documents
**Proposed guest API:** no third-party signup; selective ID/detail/search/genre/AND facet/ranked list/download mirror/volume pages with strict parameter and field allowlists, fixed maximum pages (e.g. 20-100 items by endpoint), deterministic cursors and no unrestricted table browsing or arbitrary SQL/export. Deny anonymous base-table SELECT, enable RLS, and narrowly allow audited SQL RPC with grants or server-only Edge access. Direct PostgREST RPC can avoid counting every GET as an Edge invocation, **not** Supabase egress, database reads or abuse. If using SECURITY DEFINER SQL, pin search_path and limit execution privilege. Publisher routes must be separately authenticated/isolated; client stores no privileged API or database credential.
**Official [S5]:** Supabase publishable/legacy anon keys can appear in desktop binaries only because they are public low-privilege identifiers, *not* proof of client identity. Secret/service role bypasses RLS and MUST stay on controlled backends. Any public no-signup API can be scripted: headers, app labels, reverse engineering obstacles, free guest HMAC leases and client-issued anonymous identities do not enforce 'app-only'. A guest issuer may help abuse response but is not cryptographic client attestation. Optional Supabase anonymous Auth adds MAU/session churn and must not force users to register. State truthfully: only Colosseum apps are the intended consumers; exclusivity is unprovable.
**Proposed content publication:** immutable world/tribute/version/record Storage paths, small signed/hashed manifest with schema version, min supported native renderer, stable IDs, provenance and SHA-256 for each record; live version pointer changed atomically; maintain previous versions and rollback pointer (not overwriting immutable cached objects) under quota. Publish Universe and Tribute *content*, not executable QML, so new renderer features require app release. Selective JSON records/pages only; never content packs. MusicBrainz API cached selective enrichment, optional Wikidata, no full mirror. Respect distinct canonical worlds (Tankoban, Biblio, Theatre, Universes, Vault) and styled Tributes.
**Client/offline plan:** native async C++/Qt adapters replacing sync SQLite calls, cancellation and bounded retries, explicit Ready/Empty/Error, stable caches per query/version and a bounded last-valid offline cache. HTTPS, content hash verification, schema/body size bounds, ETag/Cache-Control, canonical cache keys, request coalescing, safe placeholders for unavailable external art; no remote override of local identity/library/history/progress/preferences. Do not cache user-related credentials or publisher responses in shared CDN.
**While R2 is pending:** Supabase Storage can host a bounded *candidate pilot* without any R2 registration. Keep manifest references logical and origin-independent; if R2 later becomes activated and a separate decision authorizes it, copy immutable objects, verify SHA-256 and cache behavior, change versioned origin pointer with rollback, and only then remove Supabase copies. Do not assume R2 is enabled or that current D1 datasets automatically migrate. No setup call is authorized.

# 5. Workload and cache-hit/read amplification estimates
Assume 30 days; 30 API GETs/DAU/day; 20,000 compressed bytes/response, excluding headers, ancillary API calls and ALL assets. '90% hit' means requests are satisfied before Supabase origin (client cache or upstream Worker cache), *not* just Supabase Storage cached-egress accounting. SQL sensitivity: 1 to 5 database statements per Supabase origin GET, before any within-query row-scan amplification.
| DAU | Dynamic requests/day and /month | 0% cache: dynamic origin bytes/month | 90% upstream hit: origin requests and bytes/month | SQL statements/month at 90% hit (1-5/GET) |
|---|---|---|---|---|
| 100 | 3k / 90k | 1.8 GB | 9k / 0.18 GB | 9k-45k |
| 1,000 | 30k / 900k | 18 GB | 90k / 1.8 GB | 90k-450k |
| 5,000 | 150k / 4.5m | 90 GB | 450k / 9 GB | 450k-2.25m |

**Arithmetic:** At 20 KB, 5 GB uncached origin permits ~250,000 dynamic responses/month = ~278 DAU with zero upstream hits and no asset bandwidth. Requiring <=5 GB origin bytes means >=72.2% upstream byte savings at 1k DAU, >=94.4% at 5k (90% still sends 9 GB). Edge Functions for *every* GET exhaust 500k/month above ~556 DAU unless hits bypass functions; at 1k and 5k DAU require >=44.4% and >=88.9% Edge-function bypass, respectively. Direct SQL RPC avoids that counter only. At 0% hits and 1-5 SQL/origin GET: 90k-450k, 900k-4.5m, 4.5m-22.5m statements/month for 100/1k/5k respectively; scanned rows/CPU can be much larger. These are scenarios, not observed egress, query counts or sustained performance.
**Assets separately:** Illustrative 0.5 MB/DAU/day of art = 1.5/15/75 GB/month at 100/1k/5k DAU, in addition to API bytes. Supabase Storage cached 5 GB and uncached 5 GB are different quotas; images served from external URLs use other hosts, not magically unmetered Supabase bandwidth. CDN cold misses, region, version fanout, unique signed URLs and URL parameter variance matter. Supabase Free has Basic CDN, not Smart CDN.
**Geo and cold-cache checks:** One Postgres region can be far from an Edge function near the reader. Index performance, connection pooling, query count, origin RTT, cache warmup and shared Free CPU must be tested with realistic selectivity and cold/warm requests from India, Europe and North America. No p50/p95 claim, no live benchmark.

# 6. Optional Cloudflare Worker Free: qualified answer
**Official [S6]:** Worker Free has 100,000 inbound requests/day and 10 ms CPU/invocation; cache hits inside the Worker still count as inbound requests; optional KV and Hyperdrive have their own Free operation/query ceilings. Worker routing cannot increase Supabase DB/Storage/egress allowances.
**Useful only if validated:** With cacheable *shared anonymous* list pages, immutable Universe/Tribute content and normalized GET keys, an optional Worker can cache responses upstream of Supabase, reduce origin bytes and Edge invocations, add inexpensive request validation, and stay within 100k/day at 100 or 1k DAU if traffic is even. Measure actual per-POP hit rates, invalidation and security. Avoid new KV/Hyperdrive dependence unless separately justified.
**Disqualifier at 5k DAU:** 5,000 x 30 = 150,000 incoming Worker requests/day even with 100% Worker-cache hit: above Free. At least one-third of calls must be eliminated *before reaching Worker*, or it cannot front all traffic for $0. At 1k DAU, its ~30k/day inbound count fits but Supabase still needs >=72.2% upstream byte avoidance. Local personal state improves public cacheability but does not guarantee a hit rate. Adding Worker is not automatically beneficial.

# 7. Failure, migration, portability, decision gate
**Failures:** free project inactivity pause; 402 quota restrictions; 500 MB read-only; Edge/egress exhaustion; DB index bloat and CPU bottleneck; signed URL cache misses; failed publishing/version swaps; compromised publisher key; malicious high-rate anonymous calls; external art outages; lack of free automatic DB backup. Preserve independent local source extracts, schema/migration and versioned manifests with a reproducible backup/restore verification plan; do not claim backups or disaster recovery are tested.
**Migration effort:** Postgres schema/COPY loader, 24-table feature dependency inventory, query/regression parity, new publisher and storage contract instead of current D1 Worker, guest security, error handling, C++/Qt async remote adapters and bounded offline caches. Current 2 D1 staging DBs, 24,208 rows and 7+10 passing tests do not transfer automatically. Existing release 1.1.9 stays scoped: **NO Feria, NO Vinyl.**
**Reconsideration gates:** full source-to-feature inventory and indexed DB <=375 MB measured; restartable Free bulk import timed without multiweek delay; search/rank/filter/mirrors/volume synthesis result parity; proven origin egress/assets below Free at target DAU with cache misses and geographic cold starts; verified immutable version/rollback, backup/restore, client offline behavior and abuse/error limits. None satisfied by research alone.
**Which rival could beat it?** Workers + Neon Free PostgreSQL + R2 Standard could retain Postgres join expressiveness while separating docs and low-egress assets, *conditional* on a separate independent proof of Neon free compute/connection/usage limits and R2 enablement. Workers + D1 + R2 has more attractive document/egress headroom but must address the already-quantified D1 indexed-write bootstrap using a genuinely parity-proven smaller projection. These are comparative hypotheses only, not another review.
