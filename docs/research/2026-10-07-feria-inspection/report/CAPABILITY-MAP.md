## Cross-cutting replacement consequences

- Public Qt APIs replace operations, not app-owned consent or canonical persistence.
- Engine-internal Chromium WebContents/base/Mojo/media_session and Chrome Views/profile services cannot be passed a QML WebEngineView. Direct ports require a named Qt integration extension, matching Chromium fork, build/security upkeep and target-platform testing. No examined V1 gap presently justifies that cost before supported API probes.
- Preserving account/store authority does not require keeping its current algorithms forever. A replacement needs a tested migration and one writer; the inspected alternatives do not currently beat QSaveFile plus validation for this bounded dataset.
- The main frontend change is **session-bound host state**, rather than styling a singleton active browser. Every command and callback must carry exact session/page ownership. See FRONTEND-INTERFACE.md.
- Existing assertions that express the superseded automatic-restore/background-audio policies must be deliberately revised in the later implementation, with replacement acceptance cases. Passing old tests is not the new contract.
