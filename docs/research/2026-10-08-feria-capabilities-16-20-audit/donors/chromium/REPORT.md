# Chromium source audit: categories 16–20

Upstream comparison: Chromium 140.0.7339.264, `56ca847e9ea70a5c56fa3d634361da1002fb284b`. Receiving engine check: QtWebEngine 6.11.1 vendor gitlink `58c11ad487f8a237cf0ac71cc3e818b52db150df`. Exact donor lineage is in [../PINS.md](../PINS.md).

This is source inspection only. Named tests were read, not run. No engine build, production edit, platform/provider qualification or Chromium148 API assumption. Chromium content/components/Blink APIs are not callable public QtWebEngine APIs. Chrome browser orchestration is separately marked upstream-only; these files were not available at the exact Qt vendor paths. Shared engine behavior is not three independent donor corroborations.

## Decision summary

Keep current app pause, profile download listener, native transfer projection and canonical metadata store. Adapt immutable request identity, pause reason/retirement, typed action results, file-availability checks, late-write and Save-context negative controls. Use Qt-supported interfaces for implementation. Do not copy Chromium internals, Chrome history/cache or a separate downloader.

## Revision and fork checks

The Qt top-level metadata says base .264/security backports through148; imported Chromium/chrome VERSION remains .225. The exact vendor SHA wins. Files were fetched through Qt’s official GitHub mirror at that independently verified SHA. [Manifest](../../source/chromium/MANIFEST.json) records URLs, hashes, successful files, unsuccessful candidate paths and byte comparisons; [full diff](../../source/chromium/vendor-vs-upstream.diff) preserves differences. A failed candidate filename is not evidence that an entire capability is absent.

Relevant fork differences: MediaSessionImpl has later guards for asynchronous single-player actions and source-title handling; suspend/resume reason logic examined here is unchanged apart from line shifts. DownloadManagerImpl has a bool conversion change; DownloadRequestUtils main-frame helper now calls RenderFrameHost::CreateDownloadUrlParameters rather than manually constructing parameters; its IsURLSafe policy check is unchanged. InProgressDownloadManager has a handler-ID cast cleanup; SavePackage has aggregate-construction compatibility syntax. DownloadItemImpl, DownloadItemUtils and examined associated tests compare byte-identically. WebContents has Qt fullscreen/color/namespace changes and security backports, so entire-file equivalence is explicitly false; the inspected save/freeze behavior remains source-verified in the vendor file. Chrome download/history/target/context-menu files exist upstream but were 404 at exact vendor paths and are not treated as Qt implementation.

### Limitations and comparison

- kSystem is shared with system/audio-focus behavior and does not identify Colosseum app/world-away ownership or exact document generation. The controller activation TODO is a concrete reason not to transplant it.
- Session aggregation and routed site handlers do not control every HTML media element, silent video, one-shot/ambient player, WebAudio or third-party player. Cross-origin frame internals are available to Chromium, not necessarily to a Qt script adapter.
- Inspected browser fixtures configure no-user-gesture autoplay. They do not qualify production autoplay, provider licences, DRM or consent lifetimes.
- App display/minimize reasons and ordinary inactive-tab policy are embedder policy, not established by these classes; preserve current app semantics. Freeze is optional and needs all pending-operation blockers, not merely inaudibility.

- **Correctness:** Useful source-of-pause negative control, but coarse session ownership and frame activation hazard.
- **Targeting:** Native frame/player identity and retirement are stronger than selected-tab retargeting; no portable Qt exposure.
- **Privacy:** Session bound to WebContents/BrowserContext; no Colosseum account/space token.
- **Concurrency:** Multiple players and WebContents sessions; topmost site-service action routing is aggregate.
- **Resource Cost:** Existing engine media sessions already exist; a second polling/control service adds needless work. Freeze changes task execution, not just CPU policy.
- **Portability Maintainability:** Engine-internal Mojo, audio-focus delegates, content/Blink dependencies. Behavior adaptation is maintainable; copying/patching is not justified.

**Recommendation classifications:** Keep existing Colosseum implementation; Adapt donor behavior into an existing Colosseum owner; Internal reference only / engine patch required / unsupported / unresolved.
