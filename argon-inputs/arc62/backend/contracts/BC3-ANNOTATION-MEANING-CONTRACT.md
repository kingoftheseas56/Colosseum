# Vinyl Backend BC3 - Annotation / Meaning Plane Contract

Status: production-intent reference contract; production Colosseum adoption pending  
Date: 2026-10-06  
Owner: Arc 62 Vinyl BC3

## Purpose

BC3 defines a provider-neutral annotation and meaning plane for Vinyl.

Annotations enrich canonical music and lyric referents. They never become lyric authority, playback authority, queue authority, timing authority, or canonical music identity.

BC3 consumes BA0 RecordingMbid and BC1 TimedTextCueId without modifying either frozen contract.

## Domain laws

1. RecordingMbid is the canonical identity of the music being enriched.
2. AnnotationId identifies one BC3 annotation record only. It is not music identity.
3. AnnotationProvider preserves BA0 ProviderId plus optional provider-owned source identity and source URL as provenance only.
4. Provider identity, provider annotation identity, or source URL never replaces RecordingMbid.
5. An AnnotationReferent is provider-neutral and belongs to exactly one RecordingMbid.
6. Referent identity is derived from canonical Recording identity plus normalized anchor data; cue-linked referents also include the exact BC1 TimedTextDocumentId revision. Annotation-provider ordering/identity never owns referent identity.
7. A timed referent points to BC1 TimedTextDocumentId + TimedTextCueId. BC3 never copies, guesses, or manufactures cue timestamps.
8. Untimed referents use deterministic normalized text/range anchors.
9. A referent may exist with zero annotations.
10. One referent may have one or many annotations from one or many providers.
11. Annotation summary/header data is normalized plain text.
12. Annotation body state is explicit: not_loaded, loaded, unavailable, or removed.
13. A not-loaded body is a valid lazy state, not an error.
14. Unavailable and removed are valid provider outcomes and remain distinguishable.
15. Raw provider HTML is not part of the normalized BC3 domain contract.
16. Provider adapters must sanitize/normalize provider markup before constructing loaded BC3 body text.
17. Annotation absence is valid.
18. BC3 is presentation-independent. A current Listening Room panel is only one possible consumer.

## Value model

### AnnotationId

AnnotationId is a strong, opaque, bounded identifier for one normalized annotation record.

Rules:

- non-empty;
- at most 256 UTF-16 code units;
- no surrounding whitespace;
- no control characters.

It may be generated by Vinyl or deterministically mapped by an adapter. Its only authority is annotation-record identity.

### AnnotationProvider

AnnotationProvider contains:

- BA0 ProviderId;
- optional BA0 ProviderItemId sourceItemId;
- optional absolute HTTP(S) sourceUrl.

ProviderId keeps BA0 normalization. ProviderItemId remains opaque and case-preserving.

sourceItemId and sourceUrl are provenance/mapping data only. They do not participate in Recording identity or referent identity.

### AnnotationTextAnchor

Untimed text needs an anchor that survives harmless provider formatting differences.

BC3 normalizes anchor text by:

1. Unicode NFKC normalization;
2. collapsing each whitespace run to one ASCII space;
3. trimming leading/trailing whitespace.

AnnotationTextAnchor stores:

- normalizedText;
- rangeStart;
- rangeLength.

rangeStart/rangeLength use QString UTF-16 code-unit indexing over normalizedText.

The prototype creates an anchor from source text plus a fragment and occurrence ordinal, then stores the resolved normalized range. The fragment must resolve exactly after normalization. BC3 does not perform fuzzy matching.

### AnnotationReferent

AnnotationReferent contains:

- AnnotationReferentId;
- RecordingMbid;
- optional BC1 TimedTextDocumentId;
- optional BC1 TimedTextCueId;
- optional AnnotationTextAnchor.

A referent must have at least one anchor.

Valid shapes include:

- whole synchronized cue: sourceDocumentId plus cueId;
- synchronized cue fragment: sourceDocumentId plus cueId plus normalized text/range;
- untimed fragment: normalized text/range only.

Untimed referents require AnnotationTextAnchor.

AnnotationReferentId is a deterministic SHA-256-derived lane-local identity over:

- RecordingMbid;
- TimedTextDocumentId when cue-linked;
- cue identity when present;
- normalized text/range when present.

Annotation-provider data is intentionally excluded. Equivalent untimed normalized anchors for the same Recording resolve to the same referent identity. Cue-linked referents intentionally differ across timed-text document revisions even when the provider reuses the same cue string.

### Cue-linked annotation law

When BC1 has timing, BC3 stores the exact TimedTextDocumentId and TimedTextCueId. `cueLinked()` validates that the cue exists in that source document before creating the referent.

BC3 does not store a copied cue start/end merely to make an annotation look timed.

The timing owner remains BC1. `resolveCueIndexIn()` first requires RecordingMbid and TimedTextDocumentId equality, then resolves the cue ID. A provider/content revision with the same ordinal cue string returns SourceDocumentMismatch instead of migrating the annotation.

This prevents annotation data from drifting away from the authoritative cue grid.

### Untimed annotation law

Plain lyrics and other untimed text can still carry meaning.

For untimed text, BC3 uses AnnotationTextAnchor and deterministic AnnotationReferentId. It does not invent a timestamp, fake cue, or playback position.

Repeated identical fragments remain distinguishable through the resolved range/occurrence within normalized text.

### AnnotationSummary

AnnotationSummary contains:

- required normalized plain-text header;
- optional normalized plain-text summary.

The header is bounded to 512 UTF-16 code units. The optional summary is bounded to 4096.

No markup contract exists here.

### Annotation body

AnnotationBody contains:

- AnnotationBodyState;
- optional normalized plainText.

States:

- not_loaded: body has not been requested yet;
- loaded: normalized plainText is present;
- unavailable: provider/body lookup produced no available body;
- removed: provider reports the annotation/body was removed.

Only loaded carries text. Empty loaded text is invalid.

The body may therefore be lazy without making the whole Annotation unavailable.

### Annotation

Annotation contains:

- AnnotationId;
- RecordingMbid;
- AnnotationReferentId;
- AnnotationProvider;
- AnnotationSummary;
- AnnotationBody.

The RecordingMbid remains explicit even though a containing document also has one. This makes provider/canonical identity separation inspectable at the annotation boundary.

### AnnotationDocument

AnnotationDocument is the normalized collection for one RecordingMbid.

It contains:

- zero or more AnnotationReferents;
- zero or more Annotations.

Validation requires:

- every referent belongs to the document RecordingMbid;
- referent IDs are unique;
- every annotation belongs to the document RecordingMbid;
- annotation IDs are unique;
- every annotation references a referent present in the same document.

There is deliberately no one-annotation-per-referent rule.

A referent with no annotations is valid. An entirely empty document is valid.

## Provider normalization boundary

A provider adapter may ingest provider-specific DOM, JSON, IDs, URLs, or markup outside BC3.

Before data crosses into BC3 it must be reduced to:

- BA0 provider provenance;
- normalized referent anchor data;
- normalized plain-text header/summary/body;
- explicit body state.

Raw HTML is not retained as a BC3 field and is never required to render or store a normalized annotation.

BC3 itself does not scrape Genius, sanitize arbitrary HTML, execute markup, or make network calls.

## Error vocabulary

BC3 exposes lane-local typed failures:

- None
- InvalidAnnotationId
- InvalidReferent
- InvalidTextAnchor
- InvalidSummary
- InvalidProvenance
- InvalidBody
- DuplicateReferentId
- DuplicateAnnotationId
- UnknownReferent
- SourceDocumentMismatch
- UnknownTimedTextCue
- RecordingMismatch

Stable snake_case names are exposed by the prototype.

BA0 parse errors remain BA0 errors. BC1 timing/cue validation errors remain BC1 errors.

## Wave 4 document-binding acceptance

The native harness proves that a cue-linked referent carries the exact TimedTextDocumentId, resolves against that document, rejects a provider/document swap that reuses the same cue ID with SourceDocumentMismatch, and fails closed when asked to bind a cue absent from the claimed source document. Untimed text anchors remain independent of TimedTextDocumentId.
